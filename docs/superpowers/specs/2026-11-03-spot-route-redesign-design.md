# 장소 설명·동선 화면 리디자인 설계

2026-11-03 · 느린 제주 마음지도 · 두 개의 Dribbble 여행 앱 시안(Travel app concept, Travel Planner App UI)에서 둥글고 카드 중심인 모바일 느낌을 가져온다. 시안 페이지는 직접 열어 보지 못했고, 사용자가 말로 짚어 준 부분(활동 이름·방법·거리가 보이는 동선, 사진 위에 얹힌 둥근 장소 카드, 동그란 찜 버튼, 전체적인 둥근 느낌)만 반영한다.

## 왜 하는가
지금 앱은 정보는 충분한데 화면이 "목록·패널" 느낌이다. 수업 시연과 발표에서 휴대폰으로 보여 줄 때 깔끔하고 여행 앱다워 보이게 만들고 싶다. 지금의 따뜻한 느낌(계절 팔레트, 몽숨이, 귤 점수)은 그대로 살린다.

## 목표
1. 장소 설명 화면을 사진 중심의 둥근 카드 구성으로 바꾼다.
2. 동선 목록을 카드형으로 바꿔 "무엇을 하는지·얼마나 머무는지·어떻게 이동하는지"가 한눈에 보이게 한다.
3. 추천 동선과 챗 코스 카드의 제목을 그 동선의 특징(핵심 1~2개)으로 짓고, 끝말은 기분에 따라 바꾼다.
4. 전체에 둥근 모서리와 카드 느낌을 일관되게 적용한다. 모바일 화면이 기준이다.

## 하지 않는 것
- 색 토큰(`season.js` 팔레트), 몽숨이, 3D 지도, 챗 창 디자인은 바꾸지 않는다.
- 제목을 AI로 짓지 않는다. 규칙으로 만든다.
- 모바일에서 아래서 올라오는 시트(바텀 시트)는 하지 않는다.
- 새 데이터 수집이나 저장 방식 변경은 없다. 리뷰·찜·동선 저장은 지금 그대로다.

## 실패로 보는 경우
- 데스크톱 화면이 깨지거나 못생겨진다.
- 기존 기능이 사라진다: 동선에 담기, 찜, 근처 카페·식당, 사진 갤러리와 출처 표시, 리뷰 쓰기·수정.
- 귤 점수나 리뷰가 없는 장소에서 화면이 비어 보이거나 깨진다.
- 글자 줄바꿈·위치 규칙(한글 `word-break: keep-all`)이 흐트러진다.

## 사용자가 정한 것

### A. 장소 설명 화면
- 모바일에서는 핀을 누르면 화면 전체가 장소 설명으로 바뀐다(지도가 뒤에 남는 시트는 아님). 뒤로가기(‹)를 누르면 지도로 돌아온다.
- 위쪽에 장소 사진이 크게 깔리고, 그 위에 둥근 뒤로가기 버튼과 동그란 찜(♥) 버튼이 얹힌다.
- 사진 아래 둥근 카드(위쪽 모서리가 크게 둥글고 사진을 살짝 덮음)에 위에서 아래로: 카테고리 칩 → 굵은 장소 이름 → 주소(작게) → 이름 바로 아래 작은 글씨로 `🍊 3.0 · 마음지도 리뷰 12개` → 굵은 한 줄 설명 → 설명 → `동선에 담기` 버튼 → 리뷰.
- 카테고리 칩은 앱의 탭 기준(자연, 오름, 트레일, 문화, 예술, 시장, 올레코스 등)을 쓴다. 카페 같은 카카오 장소는 "카페"를 쓴다.
- 설명은 모바일에서 3줄까지만 보이고 "더보기"를 누르면 펼쳐지며 "접기"로 되돌린다. 짧은 글에는 더보기를 보이지 않는다.
- 귤 점수는 이름 아래 작게 둔다(리뷰 제목 줄이 아님). 리뷰 칸에는 실제 리뷰 글이 보인다.

### B. 동선 화면
- 카드형이다. 번호 동그라미, 활동 이름(굵게), 장소 이름, 머무는 시간 칩, 이동 방법·거리·시간 칩이 한 카드 안에 들어간다. 카드 사이에 따로 이동 줄을 두지 않는다.
- 동선 위에 기분 칩과 특징 제목, 그 아래 요약("3곳 · 걷기 2.1km · 약 2시간")을 둔다.
- 이동 수단(자동차·걷기·버스) 선택은 지금처럼 유지한다.

### C. 동선 제목
- 제목은 동선에 담긴 장소들의 종류에서 가장 많은 1~2개를 뽑아 짓는다. 예: "숲과 바다 느끼기". 기분 이름은 제목 위 칩에 따로 둔다.
- 끝말은 기분 5단계마다 다르다. 지칠수록 쉬는 느낌, 활기찰수록 느끼고 더 밝고 활발한 느낌이다.

### D. 버스 구간 세부정보 (사용자가 나중에 추가로 요청)
- 이동 수단이 버스일 때 동선 카드 안의 "버스로 이동" 줄 옆에 작게 누를 수 있는 "세부정보" 탭을 둔다.
- 누르면 이 구간에서 탈 수 있는 버스 정보가 펼쳐진다: 버스 번호, 어느 정류장에서 타서 어느 정류장에서 내리는지(어디서 어디로 이동하는지).
- 다시 누르면 접힌다.

**제 판단 (D)**
- 정보는 제주버스정보시스템 데이터로 만든다. 구간의 출발지·도착지 근처 정류장(각 1km 안, 가까운 3곳)을 찾고, 같은 노선(방향이 정해진 노선 ID)에서 승차 정류장이 하차 정류장보다 앞에 있는 직행 노선만 보여 준다. 한 번에 최대 3개, 걷는 거리와 정류장 수가 적은 순서.
- 각 항목에는 번호, "승차 정류장(걸어서 N m) → 하차 정류장(걸어서 N m)", 정류장 수, 다음 버스가 오는 예상 분(알 수 있을 때만)을 보여 준다.
- 직행이 없으면 "직접 가는 버스를 찾지 못했어요. 환승이 필요할 수 있어요"와 제주버스정보시스템 링크만 보여 준다. 환승 경로는 만들지 않는다.
- 세부정보는 동선 화면(내 동선·추천 동선)에만 둔다. 챗 코스 카드는 지금 그대로다.
- 이 데이터는 도청 사이트의 비공식 내부 주소를 쓰므로 실패하면 위 안내 문구로 대신한다.

## 제 판단 (사용자가 확인하지 않은 것)
- **굵은 한 줄 설명**: 지금 데이터에 없다. 소개글의 첫 문장을 쓴다. 첫 문장이 60자를 넘으면 굵은 줄 없이 설명 하나로만 보여 준다(구현 중 확인: 첫 문장이 40자를 넘는 곳이 59%라 잘라 쓰면 아래 설명과 같은 말이 두 번 보임).
- **끝말 예시** ("숲과 바다" 기준): 많이 지쳤어요 → "…에서 쉬어 가기", 조금 가라앉았어요 → "… 천천히 거닐기", 그저 그래요 → "… 느끼기", 괜찮아요 → "… 즐기기", 활기 넘쳐요 → "…에서 신나게 놀기". 최종 문구는 구현 때 다듬어도 된다.
- **기분 칩 이름**: "많이 지친 날", "가라앉은 날", "보통의 하루", "괜찮은 하루", "활기찬 하루".
- **종류 → 제목 낱말**: 숲·곶자왈=숲, 해변·포구·바다 이름이 든 자연=바다, 오름=오름, 카페=쉼, 시장=시장 구경, 문화·유적·사찰·박물관=옛 이야기, 예술=전시, 트레일·올레코스=걷는 길. 두 개를 이을 때는 받침에 따라 와/과. 하나뿐이면 낱말에 끝말만 붙인다.
- **활동 이름**: 장소 종류에서 정한다(예: 숲·자연=천천히 걷기, 해변=바다 소리 듣기, 카페=차 한 잔 쉬어가기, 시장=구경하며 먹기, 문화=이야기 둘러보기). 장소별로 직접 쓰지는 않는다.
- **기분이 없는 동선**(사용자가 직접 담은 "내 동선"): 기분 칩은 생략하고, 제목은 같은 규칙으로 짓되 끝말은 "느끼기"로 쓴다.
- **사진이 없는 장소**: 사진 영역은 장소 종류의 이모지와 팔레트 색 그라데이션으로 채운다(지금의 "사진은 아직 없어요" 문구는 사진 위 안내 한 줄로 작게).
- **리뷰가 없는 장소**: 이름 아래에 "아직 리뷰가 없어요"만 작게 보인다.
- 데스크톱은 같은 카드 구성을 좁은 패널 폭에서 그대로 쓴다. 풀스크린 전환은 모바일(640px 이하)만이다.

## 검토 후 정리 (코드로 확인했거나 제가 정한 것)
- **챗 코스의 기분**: 챗 코스 카드도 앱 상태의 `moodLevel`로 만들어진다(`fetchPlan(answers, moodLevel)`). 그래서 제목 짓기는 클라이언트에서 한다. `src/lib`에 제목 함수 하나를 두고 동선 화면과 챗 코스 카드가 같이 쓴다. 서버 응답 모양은 바꾸지 않는다. 챗 코스 카드에도 기분 칩을 붙인다. (확인한 사실)
- **머무는 시간과 활동 이름**: 머무는 시간 `STAY`는 장소 종류가 아니라 동선 항목의 `type`(spot·meal·rest)별이다. 활동 이름은 종류(`kind`) 기준 표를 새로 만들고, 시간 칩은 지금처럼 `STAY[type]`을 쓴다. 식사·쉬어가기 항목의 활동 이름은 type으로 정한다(meal="식사하기", rest="차 한 잔 쉬어가기"). (확인한 사실 + 제 판단)
- **카테고리 칩**: `KIND_GROUP[kind] || kind`로 쓰고, 둘 다 없으면 "기타". 카카오 장소는 type에 따라 "식당" 또는 "카페". (제 판단)
- **제목 규칙의 빈틈**: 종류 수가 같으면 동선에서 먼저 나온 것을 앞에 둔다. 낱말이 없는 종류는 세지 않고, 셀 것이 하나도 없으면 "제주 둘러보기"로 쓰고 끝말은 붙이지 않는다. 한 곳뿐인 동선은 그 곳의 낱말 하나만 쓴다. "바다" 판별은 장소 이름에 해변·포구·바다·항·해안이 든 경우로 한다. (제 판단)
- **뒤로가기(‹)**: 선택한 핀을 해제하고 지도로 돌아온다. 모바일의 하드웨어·브라우저 뒤로가기는 따로 처리하지 않는다(패널 상태만 쓰고 주소 기록은 건드리지 않음). (제 판단 — 나중에 필요하면 추가)
- **더보기**: 3줄 접기는 모바일과 데스크톱 모두에 적용한다. 패널이 좁아 같은 문제가 있기 때문이다. (제 판단)

## 지금 코드 (참고)
- 장소 설명 패널: `src/components/Explore.jsx`의 `spot ? (...)` 블록(약 520~546줄). 사진은 `Gallery`, 근처 카페·식당은 `Nearby`, 리뷰는 `ReviewBox`, 찜은 `FavButton`, 별점 표시는 `CitrusRating`.
- 별점 평균은 `src/lib/reviews.js`의 `ratingsFor`가 `{ avg, count }`로 준다.
- 동선 목록: `Explore.jsx`의 `RouteList`(약 223줄). 구간 데이터 `legs`(km, minutes, walk)와 이동 수단 `transport`(drive·walk·bus)를 이미 갖고 있다. 머무는 시간은 `STAY` 상수.
- 추천 동선 이름·기분: `src/lib/suggest.js`, `src/lib/moods.js`(기분 5단계, `KIND_GROUP`, `KIND_EMOJI`).
- 챗 코스 카드: `src/components/ChatFab.jsx`, `server/plan.js`.
- 스타일: `src/styles/theme.css`(모바일 구간은 `@media (max-width: 640px)`).
- 글자 위치만 만지던 기존 디자인 규칙은 이번 요청으로 범위가 넓어졌다. 팔레트·마스코트·지도는 그대로 둔다.

## 구현자에게 맡기는 것
- 정확한 모서리 크기(반지름), 그림자, 간격, 글자 크기.
- 모바일 풀스크린 전환 방식(라우트 / 패널 상태)과 전환 애니메이션.
- 소개글에서 첫 문장을 자르는 방법과 "더보기" 필요 여부 판단 방법.
- 종류 → 낱말 규칙의 세부 표와 받침 판별 방법.
- 사진·리뷰가 없을 때의 정확한 모양.
